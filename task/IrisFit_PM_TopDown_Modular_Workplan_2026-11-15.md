# IrisFit Top-Down 단계별 개발·QA 운영안

- 작성일: 2026-11-15
- 작성 역할: 수석 PM
- 문서 상태: **작업 운영 제안 — 제품/정책 결정은 별도 승인**
- 대상: IrisFit (`com.eyeoverlay.app`)
- 출시 상태: **Release Hold**

## 1. PM 방침

큰 제품 구조와 우선순위를 먼저 정하고, 각 영역을 독립적으로 검토한 뒤 필요한 부분만 작은 개발·QA 단위로 전달한다. 서로 영향이 없는 작업은 분리하고, 공통 인터페이스나 저장/점수/권한 같은 의존성이 있으면 선행 작업과 통합 순서를 명시한다.

개발자와 QA에게 전체 문서와 모든 세부사항을 한 번에 전달하지 않는다. PM은 전체 계획과 의존관계를 관리하고, 각 담당자는 자신이 맡은 작업에 필요한 요구사항·관련 코드 범위·테스트 기준·선행조건만 받는다. 제품 범위나 정책 결정이 필요한 정보는 감추지 않고 명확히 표시한다.

완료된 영역은 검증 증거와 버전을 기준으로 고정한다. 이후 변경이 꼭 필요하면 영향 분석, PM 승인, 회귀 테스트를 거친 변경으로 다루며 기존 완료 기록을 덮어쓰지 않는다.

## 2. 전체 큰 목차 (Top Level)

현재는 목차와 진행 순서만 정의한다. 하위 세부사항은 앞 단계 결과와 PM 승인을 받은 뒤 작성한다.

| 단계 | 영역 | 핵심 질문 | 산출물 | 다음 단계 조건 |
|---|---|---|---|---|
| 0 | 기준선 및 현재 상태 감사 | 현재 Release에 실제로 무엇이 구현되어 있는가? | 기준점, 기능 인벤토리, Release 구성/데이터/결함 보고 | QA가 감사 증거를 검토 |
| 1 | 제품 범위 및 베타 MVP 결정 | 사용자에게 어떤 핵심 가치를 최소 범위로 제공할 것인가? | PM 승인 범위, 포함/제외 기능, 사용자 약속 | 미해결 정책 결정을 확정 |
| 2 | 핵심 사용자 여정 | 설치 후 핵심 가치까지 사용자가 막힘 없이 도달하는가? | 여정별 요구사항/수용 기준 | 독립 QA 통과 |
| 3 | 데이터·권한·정책 | 필요한 데이터/권한을 투명하고 최소한으로 사용하는가? | 데이터 흐름, 고지, 권한 대체 동선, 정책 검토 | 개인정보/Play 미결 항목 해소 또는 기능 제외 승인 |
| 4 | 핵심 도메인 신뢰성 | 점수·세션·기록·날짜가 일관되고 복구 가능한가? | 도메인별 규칙, 테스트, 복구 결과 | 회귀 테스트와 영향 통합 완료 |
| 5 | 클라이언트 안정성·접근성 | 기기/OS/언어 차이에도 크래시 없이 사용 가능한가? | 접근성/기기/예외 테스트 | 베타 차단 결함 없음 |
| 6 | 출시 구성 및 스토어 준비 | 배포물·등록정보·지원체계가 실제 기능과 일치하는가? | Release 증거 및 스토어 준비 체크 | PM 내부 테스트 승인 |
| 7 | 내부 테스트 | 지정 테스터가 배포 Release를 설치해 핵심 흐름을 완료하는가? | 테스트 결과 및 수정 우선순위 | PM 베타 승인 |
| 8 | 제한 베타 | 실제 사용자에게 가치가 전달되고 신뢰/품질 기준을 만족하는가? | 피드백·품질 지표·제품 결정 | PM 정식 출시 심의 |
| 9 | 정식 출시 및 운영 | 단계적 출시와 모니터링/대응 계획이 준비되었는가? | 출시 승인, 롤아웃/중단 기준, 운영 후속 | 별도 PM Production 승인 |

## 3. 독립 작업 단위로 쪼개는 원칙

각 하위 작업은 하나의 명확한 문제와 결과를 가져야 한다. 가능한 경우 다음 항목으로 범위를 제한한다.

- 단일 사용자 여정 또는 도메인 책임
- 명시된 코드/모듈 경계와 관련 테스트
- 입력/출력 또는 API/저장소 계약
- 선행 작업과 후속 통합 지점
- 완료 판정이 가능한 acceptance criteria

분리 예시(감사 결과에 따라 재조정):

- 화면·문구 작업과 점수 계산/저장소 작업을 분리한다.
- Usage Access 안내·거부 동선은 권한 경험 단위로 분리하고 점수 정책 변경과 섞지 않는다.
- 세션 UUID/저장 멱등성은 게임 UI 디자인 변경과 분리하되 실제 ViewModel→Repository 경로를 통합 검증한다.
- 센서 자세 표시와 점수 산식은 별도 결정/작업으로 다룬다.
- AI SDK 데이터 검토는 UI 문구 작업과 분리한다. 정책 승인 전 기능 노출은 별도 PM 결정이다.
- 언어별 번역은 공통 의미/키를 먼저 확정한 뒤 언어별 검수 작업으로 나눈다.

작업 간 공유 파일, 공통 상태, 데이터 형식, 저장소, Manifest, Gradle 설정에 영향을 주면 독립 작업으로 간주하지 않는다. PM/개발자는 의존관계를 지정하고 통합 담당과 회귀 범위를 정한다.

## 4. 상세화 및 개발 전달 단계

### 4.1 전체 개요

먼저 단계 제목, 사용자 가치, 종료 조건, 선행조건만 정한다. 이 단계에서 구현 세부 설계를 미리 과도하게 작성하지 않는다.

### 4.2 영역별 요구사항

해당 영역을 시작하기 직전에만 문제, 현재 근거, 기대 동작, 예외, 정책 위험, 완료 기준을 상세화한다. 개발자에게 전달하는 작업 문서는 해당 영역에 필요한 내용으로 제한한다.

### 4.3 개발 단위

큰 요구사항을 독립 검증 가능한 작은 변경으로 나눈다. 각 단위는 담당자, 의존 작업 ID, 수정 가능한 범위, 테스트 방법, 복구/롤백 고려사항을 명시한다.

### 4.4 QA 단위

QA는 개발 완료 단위와 같은 ID를 사용하되 별도 판정한다. 최소한 수용 기준, 테스트 환경, 재현 절차, 결과 상태, 증거 및 남은 위험을 기록한다.

### 4.5 통합 확인

분리된 변경을 합친 뒤 인터페이스·데이터·권한·lifecycle 영향을 점검한다. 단위 QA 결과만으로 통합 상태를 완료 처리하지 않는다.

## 5. 전달 문서의 최소 형식

개발/QA 요청은 다음 정보만 포함하고 전체 배경 문서는 링크로 참조한다.

1. 작업 ID와 간결한 제목
2. 사용자 문제/목표 (Why)
3. 현재 확인된 사실과 근거 링크
4. 기대 결과 및 범위에 포함/제외되는 항목
5. 의존 작업/인터페이스
6. 예외 및 Play 정책 주의점
7. 측정 가능한 완료 조건과 QA 증거 요구
8. 미확인 사항/PM 결정 필요 여부

담당자에게 무관한 과거 토론, 다른 영역의 세부 구현, 관련 없는 파일 목록을 복사해 전달하지 않는다. 단, 안전·개인정보·통합에 영향을 주는 의존성은 반드시 공유한다.

## 6. 완료 영역 보호 (Change Freeze)

영역은 아래 조건을 모두 충족할 때 `완료-고정` 상태로 전환한다.

- 승인된 범위 및 완료 기준 충족
- 개발자 자체 검증 결과 보존
- QA 독립 검증 통과 또는 PM이 문서화한 잔여 위험 수용
- 관련 통합/회귀 테스트 결과와 버전/커밋 식별
- 문서 인덱스와 작업 상태 갱신

`완료-고정` 영역은 일반 작업에서 수정하지 않는다. 변경이 필요한 경우:

1. 변경 요청 ID와 사용자/정책/기술상 이유를 기록한다.
2. 고정 영역을 수정해야 하는 직접 근거와 영향 범위를 밝힌다.
3. 연관 계약, 저장 데이터, 하위 영역, 테스트 및 릴리스 위험을 분석한다.
4. PM이 변경 범위와 회귀 계획을 승인한다.
5. 변경 후 해당 영역과 연결된 통합 테스트를 재실행하고 새 버전으로 기록한다.

고정은 수정 불가능하다는 뜻이 아니라, 영향 분석과 승인 없이 회귀를 발생시키지 않는 통제다.

## 7. PM이 보는 전체 상태와 담당자별 브리프

- **PM 마스터 뷰:** 이 문서의 전체 단계, 인덱스, 결정 로그, 작업 ID, 의존성, 상태, 위험을 관리한다.
- **개발자 브리프:** 현재 맡은 작업, 선행조건, 수정 경계, 기대 동작, 검증 방법만 제공한다.
- **QA 브리프:** 해당 개발 작업의 수용 기준, 위험 기반 시나리오, 환경/증거 요구만 제공한다.
- **통합 브리프:** 여러 작업에 걸치는 인터페이스와 회귀 범위만 제공한다.

기밀 또는 정책상 중요한 맥락을 역할 분리를 이유로 누락하지 않는다. 관련이 있는 위험과 의존성은 요약해 담당자에게 전달한다.

## 8. 같은 AI가 개발자와 QA를 맡을 때의 역할 분리

개발자와 QA가 동일한 AI라도 두 역할은 하나의 혼합된 작업으로 처리하지 않는다. 각 작업 단위마다 명시적인 **Developer 단계 → QA 단계 → PM 판정**을 둔다. 이를 조직적으로 완전히 독립된 검토라고 부르지는 않으며, 역할 전환과 증거를 분리해 자기검토 편향을 줄이는 절차로 취급한다.

### Developer 단계

- 승인된 단일 작업 ID와 요구사항만 구현한다.
- 작업 전 기준점과 기존 변경을 보존하고, 수정 범위를 벗어나지 않는다.
- 구현 후 개발자 자체 테스트를 수행해 명령, 결과, 수정 파일 및 알려진 한계를 인계 자료로 작성한다.
- `개발 완료`는 자체 검증 제출을 뜻할 뿐 QA 통과를 뜻하지 않는다.
- 인계가 끝나면 QA 판정 전에 추가 수정을 멈춘다. QA가 찾은 결함을 같은 검토 기록에서 조용히 고치지 않는다.

### QA 단계

- 구현을 수행한 Developer 모드에서 벗어나 별도 QA 체크리스트와 승인된 acceptance criteria만을 기준으로 검토한다.
- 원 요구사항, 변경 파일/diff, 자체 테스트 결과를 확인하되 Developer의 결론을 사실로 전제하지 않는다.
- 가능한 경우 독립적으로 테스트를 재실행하고, 변경 코드에 대한 논리 검토와 재현 시나리오를 수행한다.
- 결과는 `PASS / FAIL / BLOCKED / NOT RUN` 중 하나로 기록하고, 각 판정에 근거와 검증 한계를 붙인다.
- QA 역할은 코드를 직접 고치지 않는다. 결함이 발견되면 ID, 재현, 기대/실제, 영향, 증거를 적어 Developer 단계로 반환한다.
- 동일 AI가 작성한 코드라는 점을 감안해 “독립 QA” 대신 **역할 분리 QA 검토**라고 표시한다. 실제 다른 사람의 독립 승인이 요구되면 그 승인 전까지는 완료로 처리하지 않는다.

### 수정 후 재검증

- Developer는 QA 결함 ID를 연결해 수정하고 영향 테스트를 실행한 뒤 새 인계 자료를 제출한다.
- QA는 해당 결함과 영향을 받는 회귀 범위를 다시 검증한다. 수정 과정에서 새로 발생한 변경/결과도 확인한다.
- QA PASS 후에도 제품 범위·정책·출시는 PM이 결정한다. AI의 QA PASS가 PM 승인이나 Release Hold 해제를 대신하지 않는다.
- 개발과 QA 결과, 실행 시각, 소스/빌드 식별, 테스트 로그 위치를 같은 작업 ID로 문서화하되 각각 구분된 항목/기록으로 남긴다.

### 역할별 응답 머리말

개발/QA 산출물에는 다음 중 하나를 명시한다.

- `[Developer] 작업 ID: ...` — 구현 범위, 변경, 자체 검증, 잔여 이슈
- `[QA] 작업 ID: ...` — acceptance criteria별 상태, 검증 증거, 발견 결함
- `[PM] 결정 ID: ...` — 승인/보류/거절, 결정 근거, 다음 범위

사용자가 역할을 변경하거나 하나의 산출물에서 서로 다른 역할의 판단을 요청하지 않는 한, 한 응답에서 Developer 구현과 QA 최종 PASS를 동시에 선언하지 않는다. 먼저 개발 인계를 제출하고 역할이 분리된 다음 QA 판정을 기록한다.

## 9. 현재 적용할 진행 순서

1. **AUD-01 현재 상태 읽기 전용 감사**를 실행한다. 기존 변경을 보존하고 코드 수정은 하지 않는다.
2. QA는 감사 근거와 상태 분류만 독립 확인한다. 아직 제품 기능 수정은 시작하지 않는다.
3. PM은 감사 결과를 바탕으로 전체 목차의 1단계(베타 MVP 범위)와 우선순위를 결정한다.
4. 각 승인 영역을 독립 ID로 상세화하고, 상호 영향이 없으면 분리해 개발/QA에 전달한다.
5. 영역별 완료·고정 후 통합 검증을 수행한다.
6. 내부 테스트, 제한 베타, Production은 각각 별도 게이트/승인으로 관리한다.

## 10. 운영 상태 기록

세부 작업마다 인덱스에 다음 상태 중 하나를 기록한다.

- `대기`: 착수 조건이 아직 충족되지 않음
- `진행`: 승인된 작업 중
- `개발 완료`: 개발자 검증 제출됨
- `QA 진행`: 독립 검증 중
- `완료-고정`: 수용 기준/QA 증거/버전이 보존되고 변경 통제 적용
- `BLOCKED`: 외부 승인/접근/정책 결정 필요
- `보류/취소`: PM 결정으로 중단

현재 세부 구현 감사 결과가 제출되기 전에는 후속 영역의 세부 요구를 한 번에 모두 작성하지 않는다.

### 📋 [개발 지시서] (To. 시니어 Android 개발자)

* **작업 목표 (Why):** 큰 제품 목표를 상호 영향이 적고 검증 가능한 작업 단위로 나누어, 한 번에 전달되는 정보량과 변경 위험을 줄이고 개발 가독성·완성도를 높인다.
* **상세 요구사항 (What):**
  - 기능 1: 전체 단계와 의존관계는 PM 마스터 문서에서 관리하고, 개발자/QA에는 현재 승인된 작업에 필요한 간결한 브리프만 전달한다.
  - 기능 2: 작업 단위를 단일 문제·명확한 모듈 경계·수용 기준으로 정의한다. 공유 저장소/인터페이스/Manifest/빌드 설정을 건드리는 작업은 독립으로 분리하지 말고 의존성/통합 계획을 명시한다.
  - 기능 3: 개발 완료 시 변경 파일, 자체 테스트, 잔여 위험을 보고하고 QA 판정 전에는 완료-고정 처리하지 않는다.
  - 기능 4: 완료된 영역은 파일/계약/테스트/버전 기준으로 고정한다. 변경 필요 시 변경 요청, 영향 분석, PM 승인 및 회귀 테스트 후 새 버전으로 기록한다.
  - 기능 5: 전체 단계의 완료 상태·작업 ID·결정·의존성을 문서 인덱스에 갱신하되 과거 기록을 덮어쓰지 않는다.
* **예외 처리 및 엣지 케이스:** 실제로 독립적이지 않은 변경, 공통 파일 충돌, 선행조건 미완료, 정책 결정 필요, QA 실패, 기존 dirty worktree를 별도 표시한다. 정보 최소화가 안전·개인정보·통합 의존성의 누락으로 이어지지 않게 한다.
* **Google Play 정책 체크포인트:** 권한·개인정보·데이터 흐름·건강 표현·결제·타겟 API 같은 출시 위험은 해당 작업 브리프에 필요한 최소 요약과 근거 링크로 포함한다. 다른 작업 문서에만 기록해 담당자가 위험을 놓치게 하지 않는다.
* **완료 조건 (Acceptance Criteria):** (1) 전체 단계 목차와 다음 승인 게이트가 문서화된다. (2) 각 개발/QA 요청이 필요한 맥락만 포함하고 범위·의존성·수용 기준을 갖춘다. (3) 독립 작업과 통합 작업이 식별된다. (4) 완료-고정 영역은 승인 없는 수정에서 보호되고 변경 시 회귀 검증 기록이 남는다. (5) 문서 인덱스에서 현재 상태와 관련 결정/증거를 찾을 수 있다.
