- 우선순위: P0 기반선 확보, P1 핵심 기능/정책 감사
- 출시 상태: **Release Hold**
- 관련 문서: `IrisFit_PM_Documentation_Index_and_Decision_Log.md`, `IrisFit_Developer_QA_Ground_Rules_2026-11-15.md`, `IrisFit_PM_Productization_Beta_to_Production_Plan_2026-11-15.md`

## 1. PM 결정

첫 작업은 현재 앱 구현에 대한 읽기 전용 감사다. 이 단계에서는 기능 추가·코드 수정·정책 변경·키 변경·Play Console 배포를 하지 않는다. 감사 결과를 PM과 QA가 검토한 후, 베타 MVP 범위와 우선 수정 항목을 별도로 승인한다.

이 순서는 기존 변경을 손실 없이 보존하고, 구현 상태와 과거 보고서를 혼동하지 않으며, 출시 전 실제 사용자 위험에 먼저 집중하기 위한 것이다.

## 2. 감사 전 기준점 확보

개발자는 저장소에서 작업하기 전에 다음을 기록한다.

- 작업 시각, 현재 branch 및 HEAD commit
- `git status --porcelain=v1 -uall`
- staged/unstaged diff 요약 및 untracked 파일 목록
- 기존 변경과 이번 감사 산출물의 구분 방법

작업 트리는 이미 변경 파일과 미추적 파일이 포함된 것으로 확인된 적이 있다. 어떤 기존 변경도 승인 없이 되돌리거나 삭제·덮어쓰지 않는다. 감사 중 오류 수정이 필요해 보여도 코드에는 손대지 말고 보고서에 등록한다.

## 3. 감사 범위와 결과물

### A. 제품 기능 인벤토리

각 기능을 `실제 구현 확인 / 부분 구현 / 데모·목업 / 미구현 / 미검증`으로 판정한다. 현재 Release source set에서 화면 진입점부터 저장소/API까지의 연결을 확인하고 근거 파일·클래스·함수를 기록한다.

포함할 기능:

- 첫 실행 및 홈 핵심 흐름
- Eye Battery 입력, 산식, 경계값, 표시 의미
- Usage Access 권한 설명·허용·거부·취소·철회
- 30초 휴식 및 운동 세션 시작·일시정지·취소·완료·저장·재시도
- 날짜 경계, 시간대 변경, 앱 재시작 후 기록 복구
- 센서별 가용성·등록·신선도·오류·화면 표현
- 알림, 위젯, 오프라인 및 저장 실패 동작
- AI Coach, PRO, 커뮤니티/릴레이의 실제 작동 여부와 사용자 노출
- 한국어·영어·일본어·스페인어의 핵심 사용자 여정

### B. Release 기술 감사

- applicationId, versionCode/versionName, minSdk/targetSdk/compileSdk
- Release merged manifest의 권한, 서비스, receiver, provider, process 선언
- Release runtime 의존성 및 제3자 SDK 목록
- Release signing 설정의 존재 여부만 확인하고 비밀 정보는 열거나 출력하지 않음
- lint, release boundary, 테스트, bundle, 네이티브 정렬 등 프로젝트의 실제 검증 태스크
- 생성된 산출물의 경로·시각·SHA-256과 서명 검증 결과. 기존 보고의 값을 재사용하지 않음
- Play Console 또는 실제 배포 설치를 수행하지 않았다면 해당 상태를 미검증/BLOCKED로 기록

### C. 개인정보 및 Play 정책 증거표

데이터 항목별로 `수집/조회`, `처리 주체와 위치`, `앱 자체 저장 위치`, `외부 전송 근거`, `보관/삭제`, `사용자 고지·선택`, `정책 반영 상태`를 기록한다.

최소 포함 데이터:

- UsageStats 기반 사용시간
- 완료 기록 및 점수
- 가속도계·자이로스코프·근접·조도 센서값/추정 자세
- 프로필·친구 응원 정보
- AI 프롬프트/응답
- 기기 식별자, 분석/진단 데이터

SDK 및 Android 시스템 서비스의 네트워크·보관·학습 처리에 대한 근거가 확인되지 않으면 `미확인`으로 남긴다. 코드에 직접 서버 호출이 없다는 이유만으로 전체 데이터 비전송을 주장하지 않는다.

### D. 결함 목록 및 PM 결정 필요 항목

결함마다 ID, 심각도(P0/P1/P2), 재현 단계 또는 재현 불가 사유, 기대/실제, 영향, 수정 제안, 최소 검증 시나리오를 작성한다. 제품 정책 결정이 필요한 경우 선택지·영향을 제시하고 결정을 요청한다.

PM 검토 전 변경하지 않을 정책 후보:

- 점수 산식 및 사용자-facing 점수 의미
- 베타에서 AI Coach, PRO, 커뮤니티 기능을 노출할지
- AI SDK 데이터 처리에 대한 제품 고지/동의
- 기존 사용자 데이터 처리 및 마이그레이션 정책
- Play 테스트 트랙과 배포 범위

## 4. 검증 방법과 보고 기준

- 코드 및 문서 조사와 실행 결과를 분리한다.
- 먼저 가장 작은 관련 자동 테스트를 실행하고, 실패/환경 문제는 원문 로그를 보존한다.
- 전체 테스트·lint·release bundle은 현재 프로젝트에서 제공되는 태스크를 확인한 후 실행하고 결과를 기록한다.
- 각 테스트 결과는 `PASS / FAIL / BLOCKED / NOT RUN` 중 하나다. 빌드 성공은 정책 준수, 실제 기기 동작 또는 Play 승인 증거가 아니다.
- 최신 테스트 수, AAB 해시, 인증서 지문, 기기/OS/설치 출처는 매 실행마다 새로 확인한다.
- 위험이 높은 데이터 삭제, 앱 제거, 서명 작업, 외부 배포는 수행하지 않는다.

* **상세 요구사항 (What):**
  - 기능 1: 저장소 기준점(branch, HEAD, status, staged/unstaged/untracked 목록)을 먼저 기록하고 기존 사용자/개발 변경을 보존한다.
  - 기능 2: Release variant에 포함되는 주요 기능을 UI→ViewModel→저장소/System API/SDK까지 추적해 실제/부분/데모/미구현/미검증으로 분류한다.
  - 기능 3: 점수·세션·기록·날짜·권한·센서·알림·위젯 및 다국어 핵심 흐름을 조사하고 결함의 재현/기대/실제/영향을 기록한다.
  - 기능 4: 권한·저장·SDK·AI를 포함한 데이터 흐름을 근거와 함께 작성한다. 전송/보관/삭제/학습 등 미확인 사항은 미확인으로 남긴다.
  - 기능 5: Release 설정/merged manifest/dependency/서명 설정/테스트 태스크를 조사하고 가능한 자동 검증을 실행한다. 비밀정보 없이 산출물과 결과를 식별한다.
  - 기능 6: 베타 MVP 후보와 위험 기반 제외 후보를 권고하되, 기능 범위·산식·데이터 정책은 PM 승인 전 변경하지 않는다.
* **예외 처리 및 엣지 케이스:** 기존 dirty worktree, 테스트 실패, 빌드 환경 차이, 권한 거부·철회, 저장 실패, 이벤트 중복, 센서 미지원, 자정/시간대 변경, 네트워크/SDK 미확인, Play Console·키·기기 접근 불가를 포함한다. 미실행/미접근 항목은 BLOCKED 또는 NOT RUN으로 보고한다. 사용자 데이터 삭제, 키 생성/교체, Play 업로드를 하지 않는다.
* **Google Play 정책 체크포인트:** Usage Access의 목적·범위 사전 고지와 거부 대체 경험, 개인정보 처리방침과 Data safety의 실제 동작 일치, 민감한 건강정보 및 의료 효능 오인 방지, 결제/구독·AI 기능의 실제 구현 표시, 현재 제출 대상 API 기준을 확인한다. 정책 준수는 증거가 없는 한 확정하지 않는다.
* **완료 조건 (Acceptance Criteria):** (1) 현재 Release 구현 및 설정 인벤토리에 코드 근거가 있다. (2) 데이터 흐름표가 앱 처리와 SDK/시스템 처리, 확인 사실과 미확인을 구분한다. (3) 결함은 P0/P1/P2와 재현/영향/수정 제안/검증 기준을 갖춘다. (4) 테스트/빌드 결과는 실제 실행 로그와 산출물 식별정보를 포함하며 실패가 숨겨지지 않는다. (5) 베타 MVP 권고 및 PM 결정 항목이 별도 표시된다. (6) 기존 변경분이 보존되고 감사 단계에서 코드·정책·배포 변경이 발생하지 않는다.
