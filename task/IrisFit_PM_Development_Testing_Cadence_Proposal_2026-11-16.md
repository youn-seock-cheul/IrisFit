# IrisFit 개발·검증 주기 효율화 제안

- **상태:** PM 제안 — 사용자 승인 전 운영 프로세스 변경 아님
- **목표:** 기능마다 전수 회귀·반복 보고를 수행하는 비용은 줄이고, 변경 위험에 맞는 검증 증거와 릴리스 통제는 유지한다.

## 결론

작은 변경마다 전체 회귀 테스트와 전수 QA를 다시 할 필요는 없다. 대신 **관련 변경을 작은 검증 가능한 묶음(batch)으로 계획하고, 변경 직후 빠른 타깃 테스트를 실행한 뒤, 묶음 단위로 통합 테스트와 QA를 한 번 수행**한다. 단, 코드 변경 직후 컴파일/해당 모듈의 타깃 테스트는 생략하지 않는다.

## 권장 운영 방식

1. **요구사항을 결과 기준으로 묶기:** 동일 사용자 흐름/상태 계약에 해당하는 변경을 하나의 배치로 관리한다. 예: 미측정 표시 배치에 relay, Wellness, Goal, AiCoach와 센서 freshness의 관련 계약 테스트를 함께 포함한다. 무관한 작업은 섞지 않는다.
2. **배치 착수 전에 기준선 고정:** 하나의 요구사항/배치 ID, 범위, 완료 기준, 제외 항목, 영향을 받는 컴포넌트와 회귀 테스트를 먼저 정한다. 진행 중 요구사항과 설계가 바뀌면 재계획한다.
3. **각 작은 변경 직후에는 빠른 검증:** 컴파일 또는 해당 모듈/계산기 단위 테스트, formatter/lint 중 관련된 빠른 검사를 실행한다. 실패를 다음 변경까지 미루지 않는다.
4. **배치 통합 시 영향 기반 회귀:** 한 배치의 관련 코드가 안정화되면 연결된 JVM 테스트, UI 테스트, 센서 경계 테스트를 한 번에 실행한다. 전체 테스트는 공유 계약/저장소/권한/앱 생명주기/빌드 설정을 건드렸거나 출시 후보를 만들 때 실행한다.
5. **QA는 배치 기준으로 독립 검수:** 각 미세 커밋을 따로 전수 QA하지 않고 배치 ID와 고정된 후보 commit을 대상으로 acceptance criteria, 부정/예외 케이스, 회귀 결과를 검증한다. 수정이 생기면 실패 항목과 영향 회귀만 재검증한 뒤, 후보 commit이 바뀌면 최종 통합 QA를 다시 고정한다.
6. **기기 검증은 안정된 후보에서 단계화:** 빠른 emulator/기기 smoke는 UI·권한·lifecycle 변경 배치에 한정한다. 정확도·전력·열 시험은 시험 기준과 protocol을 PM이 승인한 뒤 release candidate 단위로만 실행한다. 기기 테스트가 실행되지 않은 경우 `NOT RUN`으로 둔다.
7. **증거 보고는 커밋별 반복 대신 배치별 요약:** 요구사항 ID, base/final commit, 변경 파일, 타깃 테스트, 배치 회귀 결과, 미실시 테스트/잔여 위험을 단일 인계 문서에 기록한다. 각 커밋은 이 기록을 참조한다. 실패·결정·승인은 덮어쓰지 않고 같은 배치에 시간순으로 추가한다.

## IrisFit에 적용한 예시

현재 `f7a8d2d`까지 relay와 Wellness의 미측정 문구/아이콘 코드는 보완됐지만, 전용 UI 렌더링 및 sensor callback/freshness 경계 테스트는 아직 없다. 다음 개발 라운드에서는 “미측정 소비처 및 freshness 신뢰성” 배치 하나를 만들고:

- UI 상태 계약: 측정 불가/음수 점수/불일치 flag-score/측정 정상의 소비처별 기대 동작
- 센서 계약: 유효 값은 freshness 갱신, malformed/out-of-range 및 invalid timestamp는 갱신 금지
- 검증 세트: 관련 JVM 테스트 + Compose/UI 테스트 + detector 경계 테스트
- 최종 게이트: 전체 JVM suite, 변경이 공유 기반부를 건드린 경우 전체 빌드/lint, 고정 후보에 대한 QA 보고

로 진행할 수 있다. 실기기 실제 시청 정확도 및 배터리/열 시험은 이 코드 테스트와 별도 배치/승인 게이트로 유지한다. 자동 테스트가 늘어도 실제 시청시간 정확도나 Play 출시 승인을 대신하지 않는다.

## 단계별 실행과 기대 효과

| 구간 | 실행 | 목적 |
|---|---|---|
| 변경 중 | 변경 단위의 compile + 타깃 테스트 | 빠른 피드백, 원인 격리 |
| 배치 통합 | 관련 계약/회귀 테스트 전체 + UI/sensor 테스트 | 연관 기능의 상호작용 확인 |
| QA 인계 | 고정된 배치 후보 commit에 대한 독립 기준 검수 | 중복 검수와 버전 혼선 방지 |
| release candidate | 전체 관련 suite/build/lint 및 승인된 기기 시험 | 출시 후보 기준 증거 확보 |

기대 효과는 테스트를 줄이는 것이 아니라, **같은 검증을 모든 미세 변경마다 반복하지 않고 검증 범위를 위험과 영향에 맞추는 것**이다. 공통 점수 계약이나 센서 데이터 경로 변경처럼 위험도가 높은 배치는 여전히 넓은 회귀 검증을 요구한다.

## 📋 [개발 지시서] (To. 시니어 Android 개발자)

* **작업 목표 (Why):** 개발 피드백 주기를 빠르게 하면서도 검증 누락과 중복 QA를 줄일 수 있도록 다음 작업부터 배치 기반의 검증 흐름을 시범 적용한다.
* **상세 요구사항 (What):**
  - 기능 1: 다음 미측정/freshness 작업을 하나의 추적 가능한 배치 ID 아래 묶되 UI 상태 계약과 센서 freshness 계약을 구분된 하위 작업/테스트로 관리한다.
  - 기능 2: 각 하위 변경 후 관련 타깃 테스트를 실행하고, 배치 통합 시 관련 UI/JVM/sensor 경계 테스트를 모아 실행한다.
  - 기능 3: 배치 인계에는 base commit, final commit, 변경 범위, 테스트 명령/결과, 미실시 검증 및 잔여 위험을 한 번 기록하고, 각 커밋은 배치 인계에 링크한다.
  - 기능 4: 공통 API/점수 계약/저장/권한/lifecycle/build 설정 변경 또는 release candidate에는 전체 suite/build/lint 필요 여부를 영향 분석으로 결정해 기록한다.
* **예외 처리 및 엣지 케이스:** 배치 중 acceptance criteria 변경, 타깃 테스트 실패, QA 발견 결함, 후보 commit 변경 및 실기기 환경 부재 시 작업을 나누거나 재검증 범위를 넓히고 상태를 `BLOCKED`/`NOT RUN`으로 명시한다.
* **Google Play 정책 체크포인트:** 효율화를 이유로 권한·개인정보·센서·백그라운드 동작 검증을 생략하지 않는다. Play/실기기 게이트는 코드 자동 테스트와 별도다.
* **완료 조건 (Acceptance Criteria):** 다음 배치에서 요구사항 ID부터 acceptance criteria, 변경/테스트 증거, QA 결과 및 PM 판정이 연결되고, 변경 직후 타깃 테스트와 배치 통합 검증이 모두 수행된다. 본 제안은 PM이 운영 변경을 승인하기 전까지 시범 방식이며 기존 프로세스의 승인 게이트를 대체하지 않는다.
