# IrisFit PM·개발·QA 공통 요구사항 프로세스

- 작성일: 2026-11-15
- 문서 상태: **사용자 승인 공통 운영 기준**
- 적용 대상: IrisFit 제품 요구사항, 기본/상세 설계, 구현, 검증 및 변경 요청
- 기준 문서: `..\Walkthrough.md` (진입점), 통합 기준 `IrisFit_PM_User_Walkthrough.md`

## 1. 공통 원칙

1. 모든 요구사항에는 변경되지 않는 고유 ID를 부여한다.
2. 요구사항 ID는 기본설계, 상세설계, 개발 작업, 테스트 케이스, 결함, 변경 요청 및 완료 보고에서 연결해 추적한다.
3. PM은 요구사항과 기본설계, 기능별 우선순위, 목표 및 완료 기준을 정의한다.
4. PM은 QA와 함께 기본설계를 검토하고 확정한다. QA는 테스트 가능성·예외·위험을 검토하며, 제품 결정은 PM이 승인한다.
5. 개발자는 확정된 기본설계를 바탕으로 상세설계를 작성하고, 구현 세부사항과 변경 영향을 지속적으로 관리한다.
6. QA는 승인된 기본설계와 완료 기준을 기준으로 검증하고 결과·미해결 위험을 PM에게 전달한다.
7. 통과한 기능은 근거와 버전을 기록해 고정한다. 변경은 영향 분석과 승인 및 회귀 검증을 거친다.
8. 동일 AI가 개발과 QA를 맡더라도 Developer 인계 후 QA 단계로 역할을 전환한다. QA는 코드를 직접 고치지 않고 결함을 Developer에게 반환한다. 이 방식은 다른 사람의 독립 승인을 뜻하지 않는다.

## 2. 요구사항 ID 체계

ID는 한 번 발급하면 내용을 수정해도 재사용하거나 삭제하지 않는다. 요구사항이 폐기되면 상태를 `취소`로 남기고, 새 요구사항은 새 ID를 발급한다.

| 항목 | 형식 | 예시 |
|---|---|---|
| 요구사항 | `IRIS-REQ-<영역>-<번호>` | `IRIS-REQ-SESSION-001` |
| 기본설계 | `IRIS-BD-<요구사항 ID>` | `IRIS-BD-IRIS-REQ-SESSION-001` |
| 상세설계 | `IRIS-DD-<요구사항 ID>-<개정>` | `IRIS-DD-IRIS-REQ-SESSION-001-R1` |
| 개발 작업 | `IRIS-DEV-<요구사항 ID>-<번호>` | `IRIS-DEV-IRIS-REQ-SESSION-001-01` |
| 테스트 케이스 | `IRIS-TC-<요구사항 ID>-<번호>` | `IRIS-TC-IRIS-REQ-SESSION-001-01` |
| 결함 | `IRIS-BUG-<요구사항 ID>-<번호>` | `IRIS-BUG-IRIS-REQ-SESSION-001-01` |
| 변경 요청 | `IRIS-CR-<요구사항 ID>-<번호>` | `IRIS-CR-IRIS-REQ-SESSION-001-01` |

### 영역 코드

영역 코드는 목적에 맞게 추가할 수 있다. 예: `CORE`, `SESSION`, `BATTERY`, `PERMISSION`, `PRIVACY`, `SENSOR`, `AI`, `PRO`, `RELEASE`, `ACCESS`.

여러 요구사항에 걸치는 개발/테스트 항목은 한 ID에 억지로 넣지 않는다. 관련 요구사항 ID를 모두 연결하고, 작업 단위의 별도 ID를 부여한다.

## 3. 단계별 책임과 산출물

### 0단계 — 요구사항 취합 (PM)

PM은 사용자 요청, 사용자 문제, 현행 구현/리뷰/지표 근거를 모아 요구사항 후보를 정리한다.

각 요구사항은 다음을 포함한다.

- 요구사항 ID와 제목
- 사용자/비즈니스 문제와 목표
- 범위 및 제외 범위
- 우선순위와 목표 시점/마일스톤
- 기대 동작 및 예외 상황
- 측정 가능한 완료 기준
- 정책·데이터·접근성 위험
- 근거 및 미확인 사항

모호한 제품 동작, 데이터 정책, 점수 규칙 또는 출시 범위는 가정하지 않고 PM 결정 항목으로 둔다.

### 1단계 — 기능별 기본설계 (PM 주도, QA 협의)

PM은 기능 단위로 사용 흐름과 기대 동작을 정의한다. QA는 기본설계가 테스트 가능한지, 권한 거부·저장 실패·복귀 등 중요한 예외가 포함됐는지 검토한다.

기본설계에는 사용자 흐름, 상태/결과, 입력·출력, 기능 간 의존성, 오류/대체 동작, 개인정보/Play 정책 체크포인트 및 acceptance criteria를 포함한다. 구현 라이브러리·클래스 구조 같은 상세 기술 선택은 기본설계에 강제하지 않는다.

**기본설계 승인 게이트:** PM이 QA 의견을 검토하고 기본설계 개정과 acceptance criteria를 확정한다. 확정 전에는 개발에 전달하지 않는다.

### 2단계 — 개발 인계 (PM)

PM은 개발자가 실행할 수 있도록 요구사항 ID, 우선순위, 목표, 승인된 기본설계, 제외 범위, 의존 요구사항, 완료 기준 및 관련 문서 링크만 묶어 전달한다.

개발자에게 전체 배경 문서 전부를 반복 전달하지 않는다. 다만 해당 작업에 영향을 주는 정책 위험, 공통 인터페이스, 데이터 계약 및 선행 조건은 반드시 함께 전달한다.

### 3단계 — 상세설계 (Developer)

개발자는 구현 전에 요구사항 ID에 연결된 상세설계를 작성한다. 상세설계에는 다음을 포함한다.

- 기본설계의 각 acceptance criterion이 어느 컴포넌트/호출 경로로 충족되는지
- 데이터/상태 흐름 및 영속성 영향
- 오류·재시도·lifecycle·동시성 처리
- API/저장소/화면 간 계약과 의존성
- 구현 파일 범위와 기존 동작에 대한 영향
- 단위/통합/UI 검증 방안
- 기본설계와 다른 기술 선택이 필요한 경우 이유와 사용자 영향

상세설계가 기본설계의 사용자 동작·정책·완료 기준을 바꾸면 구현 전에 PM 승인을 요청한다. PM 승인 없이 기능 범위나 제품 정책을 바꾸지 않는다.

### 4단계 — 구현 및 개발자 자체 검증 (Developer)

개발자는 승인된 상세설계에 따라 변경하고, 관련 테스트를 실행한다. 기존 변경분은 보존하고 작업 시작 기준점과 변경 범위를 기록한다.

개발 인계에는 요구사항/상세설계 ID, 변경 파일, 설계 대비 차이, 실행 명령과 결과, 실패/미실행, 빌드 식별 및 잔여 위험을 포함한다. 이 상태는 `개발 완료`이지 `QA 통과`가 아니다.

### 5단계 — QA 검증 (QA)

QA는 요구사항과 승인된 기본설계의 acceptance criteria를 기준으로 검증한다. 상세설계는 구현 경로와 테스트 범위를 이해하는 자료로 사용하되, 요구사항을 대체하는 기준으로 삼지 않는다.

QA 결과는 각 기준별로 `PASS / FAIL / BLOCKED / NOT RUN`을 기록한다. 실패에는 결함 ID, 재현 절차, 기대/실제, 영향, 증거 및 개발자 반환 상태를 포함한다.

### 6단계 — 결함 수정/재검증 및 기능 완료

개발자는 QA가 반환한 결함 ID에 연결해 수정하고 자체 검증을 갱신한다. QA는 같은 요구사항과 영향 범위를 재검증한다.

모든 필수 acceptance criteria가 통과하고 차단 결함이 없으면 PM에게 결과를 전달한다. PM은 기능을 `완료-고정`, `조건부 완료`, `재작업`, `보류` 중 하나로 판정한다. PM 판정 후에만 기본설계, 상세설계, 테스트, 버전/커밋 및 관련 증거를 완료 기록으로 연결한다.

## 4. 변경 요구사항 처리

개발 중간 또는 기능 완료 후 새 요구가 생기면 원 요구사항을 조용히 바꾸지 않는다.

1. `IRIS-CR-...` ID를 발급하고 요청 사유와 사용자/정책 영향을 기록한다.
2. 영향받는 요구사항, 기본/상세설계, 코드, 테스트, 데이터 호환 및 완료-고정 영역을 연결한다.
3. PM이 우선순위와 범위를 승인 또는 보류한다.
4. 승인되면 요구사항/기본설계를 개정하고 QA가 테스트 기준을 보완한다.
5. 개발자는 상세설계 개정과 구현을 수행하고, QA는 변경 및 회귀를 검증한다.
6. 기존 요구사항/개정 이력은 유지한다. 완료한 변경은 새 설계/빌드 기준으로 고정한다.

긴급 보안/개인정보/데이터 무결성 위험은 일반 우선순위 조정 전에 PM에게 즉시 알린다. 단, 긴급하다는 이유로 승인·증거·회귀 기록을 생략하지 않는다.

## 5. 추적성 매트릭스

모든 기능은 다음 연결을 유지한다.

`사용자 근거 → 요구사항 ID → PM 기본설계/QA 협의 승인 → Developer 상세설계 → 개발 작업/코드 변경 → 테스트 케이스/실행 증거 → 결함/변경 요청 → PM 완료 판정`

| 요구사항 ID | 우선순위/상태 | 기본설계 | 설계 승인 | 상세설계 개정 | 개발 작업 | 테스트/QA 결과 | 결함/변경 | PM 판정 |
|---|---|---|---|---|---|---|---|---|
| 예: `IRIS-REQ-SESSION-001` | P1 / 제안 | 링크 | 미승인 | 미작성 | 미분해 | 미작성 | 없음 | 결정 대기 |

완료된 행도 삭제하지 않는다. 변경이 있을 경우 이전 판정을 보존하고 새 개정/결정으로 연결한다.

## 6. 문서 외 도구 사용 제안

문서만 사용하는 것보다 **문서 + 작업 보드 + 코드/테스트 링크**를 함께 사용하는 편이 진행 추적에 유리하다.

- 문서는 사용자 요구, PM 기본설계, 결정 근거, 상세설계 및 검증 보고의 정본으로 둔다.
- GitHub Issues 또는 동등한 이슈 추적 도구는 요구사항/개발/QA 작업의 담당자, 상태, 우선순위, 의존성, 목표 시점 및 댓글을 추적하는 데 사용한다.
- 각 Issue 제목과 본문에 해당 `IRIS-REQ-*` ID를 넣고, 기본설계/상세설계 문서와 테스트 결과를 링크한다.
- GitHub Projects 또는 동등한 보드는 `요구사항 수집 → 기본설계 검토 → 승인 대기 → 상세설계 → 개발 → QA → PM 판정 → 완료-고정` 상태를 시각적으로 보여준다.
- Pull Request, commit, test run은 해당 작업/요구사항 ID를 포함해 코드와 증거를 연결한다.
- Issue/보드는 문서의 승인된 요구사항을 대체하지 않는다. 보드 상태 변경만으로 기본설계 승인이나 출시 승인이 되지 않는다.

**권고:** 우선 문서 인덱스와 ID 체계를 정착시키고, 이후 팀이 이미 사용하는 GitHub Issues/Projects가 있다면 같은 ID로 연동한다. 새 도구 도입 자체를 선행 차단으로 만들 필요는 없다.

## 7. 상태 이름과 승인 권한

| 상태 | 의미 | 승인/담당 |
|---|---|---|
| 요구사항 후보 | 취합 중, 아직 합의되지 않음 | PM |
| 기본설계 검토 | PM 기본설계에 QA 의견 수렴 중 | PM + QA 자문 |
| 기본설계 승인 | acceptance criteria 포함 설계 기준선 확정 | PM |
| 상세설계 검토 | 개발자가 기술 설계를 작성, 기준선 변경 여부 확인 중 | Developer; 정책 변경은 PM |
| 개발 중 | 승인된 상세설계에 따라 구현 | Developer |
| 개발 완료 | 자체 검증과 인계 제출 | Developer |
| QA 중 | acceptance criteria별 독립 역할 검증 | QA |
| 재작업 | QA 결함 반환, 수정 필요 | Developer |
| PM 판정 대기 | 필수 QA 결과 제출됨 | PM |
| 완료-고정 | PM 완료 판정 및 추적성/증거 보존 | PM |
| 보류/취소 | PM 결정으로 정지/범위 제외 | PM |

단계 상태를 담당자 판단만으로 건너뛰지 않는다. 요구사항이 승인되지 않았으면 구현 시작 금지, QA가 끝나지 않았으면 QA 통과/기능 완료 선언 금지, PM이 승인하지 않았으면 베타/출시 범위 확정 금지다.

## 8. 다음 적용

현재 진행 중인 첫 작업은 `AUD-01` 현재 상태 **읽기 전용 감사**다. 제품 기능 요구사항의 구현 작업은 아직 승인되지 않았다.

이 공통 프로세스 적용 순서:

1. 감사 작업에는 `AUD-01` 작업 추적 ID를 사용하고, 감사 결과로 나온 기능 요구마다 `IRIS-REQ-*` ID를 발급한다.
2. QA는 감사 결과를 검증하고, PM은 베타 우선순위와 기능별 요구사항을 정리한다.
3. 사용자/PM과 QA가 기능별 기본설계 및 완료 기준을 확정한다.
4. PM이 확정한 요구사항만 기능별 Developer 브리프로 전달한다.
5. Developer 상세설계 → 구현/자체 검증 → QA 검증 → PM 완료 판정의 순서를 적용한다.

### 📋 [개발 지시서] (To. 시니어 Android 개발자)

* **작업 목표 (Why):** PM·Developer·QA가 요구사항부터 설계·구현·테스트·완료 판정까지 동일 ID로 연결해 변경 누락과 역할 혼선을 줄인다.
* **상세 요구사항 (What):**
  - 기능 1: 요구사항 ID, 기본설계, 상세설계, 개발 작업, 테스트, 결함, 변경 요청에 공통 추적 ID/관계를 적용한다.
  - 기능 2: PM과 QA가 확정한 기본설계 및 acceptance criteria를 구현 기준으로 사용한다. 승인된 범위와 완료 기준을 변경하지 않는다.
  - 기능 3: 구현 전에 요구사항 ID에 연결된 상세설계를 작성하고 데이터/상태 흐름, 오류·lifecycle·동시성, 변경 파일, 검증 전략과 기본설계 편차를 기록한다.
  - 기능 4: 설계 편차가 사용자 동작·정책·acceptance criteria를 바꾸면 구현 전에 PM 승인을 요청한다.
  - 기능 5: 개발 인계와 QA 결과를 역할별로 별도 기록하며, 실패는 결함 ID로 Developer에게 반환하고 수정 후 QA 재검증한다.
  - 기능 6: 완료된 기능은 PM 판정 및 증거 보존 후 완료-고정하고, 후속 변경은 `IRIS-CR-*` 영향 분석/승인/회귀로 관리한다.
* **예외 처리 및 엣지 케이스:** 상충 요구사항, 신규 요구, 의존성 변경, 저장/데이터 호환성, QA BLOCKED/미실행, dirty worktree 및 완료 영역 변경을 추적한다. ID를 재사용하거나 과거 설계/판정을 덮어쓰지 않는다.
* **Google Play 정책 체크포인트:** 권한·개인정보·SDK/AI·건강 표현·결제 및 배포 조건을 기능 기본설계와 해당 테스트 케이스에 연결한다. 정책 관련 미확인 사항은 승인된 설계/완료 상태로 표시하지 않는다.
* **완료 조건 (Acceptance Criteria):** (1) 각 구현 기능이 사용자 근거에서 PM 기본설계, Developer 상세설계, 코드/테스트, QA 결과 및 PM 판정까지 ID로 추적된다. (2) 기본설계는 QA 의견을 반영하고 PM 승인 후 개발에 전달된다. (3) 상세설계는 기본설계와 차이를 명시하며 정책/범위 변경에는 사전 승인이 있다. (4) QA 실패와 수정/재검증이 동일 ID 체계로 연결된다. (5) 완료-고정 영역은 승인된 변경 요청 없이 수정되지 않는다.
